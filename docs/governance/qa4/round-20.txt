The base checkout does protect `scripts/` and `uv.lock`: the budget that ran is `main`'s. It does not protect the
job: `pull_request` executes the workflow **as the PR has it**, with the PR's `uses:` lines and `run:` bodies.

- **#159 widened the surface.** The previous workflow ran only `fetch-metadata` before its `gh` calls
  (`git show a057807^:…` has one `uses:`). #159 added `checkout` and `setup-uv` to the job holding the token.
  A SHA-pin protects until Dependabot proposes a new SHA; from then on, the first thing that runs it is this job,
  with write, before required checks.
- **The token reaches the action:** the step log shows `with: github-token: ***` for setup-uv, whose default is `github.token`. The commit message
  ("The budget runs from main's code, never the pull request's") states the belief this disproves.
- **Why P2, not P1:** Dependabot-triggered runs get `secrets: Dependabot` only, and branch protection holds
  `main`. A malicious bump can still write other refs or tags and queue merges.
- **The unqueue job holds `contents: write` too**, but needs only `pull-requests: write`.

**Fix:** split it. A read-only job checks out `main` and answers the budget through a step output. A separate job
(`needs:` it, `if:` the output) holds `pull-requests: write` and uses no third-party action, only `gh` on the
runner. Or use `pull_request_target` with no checkout of the head, which runs the base's workflow. Add a test that
walks every `uses:` in a job with `contents: write`, and that the unqueue job holds least privilege.

A merge queued with `gh pr merge --auto` under `GITHUB_TOKEN` is performed as `github-actions[bot]`, and events made
by `GITHUB_TOKEN` do not start workflows. So the `push` this job exists for, a Dependabot auto-merge moving `main`
while another update is queued, cannot fire it.

- **What is actually holding the budget:** `strict: true` makes the second queued PR BEHIND; Dependabot rebases it;
  that `synchronize` re-runs the `pull_request` job, which re-asks and calls `--disable-auto` (the #129/#131 pair
  shows the rebase and re-run). Turn `strict` off and a second armed update merges past the reserve, and the
  documented control does nothing. C7 still stops at 11, so the loss is the reserve, not the audit gate.
- **Same mechanism, wider effect:** none of those 13 commits has a CI run on `main`. They were tested as PR merge
  refs, but every push-only job skipped them, and QA-6's "CI verified green on the release commit" cannot be
  answered from `main` if the release commit is an auto-merge.
- **The `push` branch is not unexercised**, against the prompt: run 40551713187 (a057807, a maintainer merge) ran
  it, printed `WAIT — main is 10/10 …`, listed nothing and did nothing.

**Fix:** either enable auto-merge with a GitHub App/PAT token so the resulting push fires workflows (which also
restores CI on those commits), or reword the workflow comment and the script's docstring to name `strict` and the
rebase as the mechanism, and add a test or gate that the branch-protection payload keeps `strict: true`
(`scripts/setup_branch_protection.sh`).
